01 — Start here

What this is, in plain English

RapidInsight Studio takes a description of a business's data — just the column names and types, nothing sensitive — and turns it into a full, working analytics product: real database tables, thousands of realistic rows that behave the way real data behaves, and a dashboard of charts and KPIs with written commentary. A person does this today by hand, with a spreadsheet, a SQL editor, and a BI tool. This application does it in under a minute, starting from a file upload.

The problem it solves

Selling or prototyping a data product usually stalls on one thing: real data. Customers won't hand over live sales or patient records before a contract is signed, and legal review of a data-sharing agreement can take weeks. Meanwhile, engineers building a new dashboard need something to build against, and randomly-generated placeholder data (a tool like Faker) produces rows that are individually plausible but collectively meaningless — a customer in "Tokyo" whose country is "Brazil," an order total that doesn't match its own quantity and price. A dashboard built on that kind of data shows flat, meaningless charts, because there was never a real pattern in the data to chart.

How it solves it

The application asks an AI language model to write a small batch of realistic example rows for each table — the AI already knows that a VIP customer segment should skew toward higher spending, or that a pediatric hospital ward should skew toward younger patients, without anyone coding that rule in. Those examples are then handed to a statistical model (SDV — Synthetic Data Vault) that learns how the columns move together and expands a few hundred realistic examples into thousands of rows that keep the same relationships. A separate layer of code guarantees that IDs are always unique and that every foreign key points at a row that actually exists — something a statistical model alone can only make likely, not guaranteed. On top of that finished dataset, the AI is asked a second, different question: which KPIs and charts would actually be interesting here, and it writes the SQL to compute them.

Why this design, not one big AI call

Writing 10,000 realistic rows with an AI model directly would be slow, expensive, and would start visibly repeating itself after about 40 rows. Splitting the job — AI for realism, statistics for volume, hand-written code for anything that must never be wrong (IDs, foreign keys) — is what makes the result both trustworthy and affordable to generate.

02 — Start here

Architecture at a glance

The backend is nine small services instead of one large one — a "microservice" design. Each service owns one job and can be understood, tested, and restarted on its own. Nothing outside the network can reach any service except the Gateway; every other service only trusts requests that carry a shared internal password, so a bug in one service can't be used to reach another directly from the internet.

Figure 1. How a browser request reaches the right service, and which services call each other internally.

Two services — AI Service and SDV Service — are never reachable from the Gateway at all. They exist purely to be called by other backend services, which keeps the only two components holding AI-provider credentials or running statistical model training safely out of reach of the public internet.

03 — Start here

The core pipeline: from a schema to a dashboard

Everything the product does happens in two separate moments — once quietly in the background right after a file is uploaded, and once when the user actually presses "Generate Tables." Splitting it this way is a deliberate design decision: the slow part (asking an AI to write example rows) happens while the user is still looking at the upload screen, not while they're staring at a loading spinner.

Figure 2. The two-phase pipeline — the slow AI work for example rows happens quietly at upload time; clicking "Generate Tables" only ever waits on two more AI calls plus fast statistical generation.

Two ways in: your data, or ours

Every schema uploaded to a project takes one of two paths, chosen per file, not per project — a single project can mix both. "Use my data" is for a file that already has real rows: nothing needs to be written for it, so there's nothing to wait for — it's marked ready the instant it's uploaded. "Generate mock data" is for a file that's just a column layout with no rows yet; the AI writes 50–300 realistic example rows for it in the background (the upload-time half of Figure 2), which takes roughly 30–60 seconds per table.

That background step is why the AI writes example rows at upload time instead of waiting for the "Generate Tables" click: uploads happen one at a time, sometimes minutes or days apart, so the 30–60 second cost per table never bunches up. If it ran on click instead, a ten-table project would spend ten minutes inside a single button press and risk timing out. By the time "Generate Tables" is actually pressed, every file's example rows are already sitting in storage — the button itself then only ever waits on two more AI calls plus the fast statistical step, never on writing examples from scratch.

The "Generate Tables" button stays disabled until every file in the project is ready — for a "Generate mock data" file, that means the AI has finished writing and validating its example rows; for a "Use my data" file, it's ready immediately, since there's no writing step to wait on. One distinction worth being precise about: this gate is about example rows being ready, not about SDV. SDV — the statistics engine that turns a handful of example rows into a full dataset — never runs until "Generate Tables" is actually clicked (the generate-time half of Figure 2); it plays no part in whether the button is enabled.

Why the example rows matter so much

The reason this pipeline writes real example rows before touching a statistics engine at all — rather than generating everything from column definitions alone — comes down to one measured failure. A plain column named city holding values like Tokyo, Paris, and Berlin was, in an early attempt, generated purely by a statistical model with no real examples to learn from — and it produced correct-sounding city names paired with the wrong countries roughly half the time (44–51% correct). The model was learning that Tokyo and Japan are correlated, never that Tokyo determines Japan.

The fix: detect these pairs directly from the example rows — if every value of one column appears with exactly one value of another column across every example row seen, that's a determining pair — and hand it to SDV as a fixed_combinations constraint, which restricts what SDV is allowed to generate to combinations that actually appeared in the examples. That took city/country from ~50% to 100% correct, with no city/country-specific code anywhere: the same detection catches product/category, state/region, or any other domain's determining pair, because it's discovered from the data, not hardcoded.

Why are we using what? Not every structural relationship gets handed to SDV this way — that decision was made per relationship type, based on what testing actually showed, not on a general rule of thumb:

  • Categorical determinism (city/country) → given to SDV directly, as a native fixed_combinations constraint. Testing showed no side effects: ordering held, other correlations were unaffected.
  • Date ordering (a delivery date after its order date) → deliberately kept out of SDV. An inequality constraint was tried first and measured to actively invert an unrelated correlation: a clean 49/293/895 segment-to-price signal came out as 187/290/254 with the constraint applied — worse than the 157/251/541 result of removing the constraint entirely. SDV enforces ordering by substituting a difference for the later column before fitting, and that transformation distorted the rest of the table; it also slowed one generation from 8 seconds to 46. So instead, the later date column is removed from what SDV sees entirely, and computed afterward as earlier date + a gap sampled from the real example rows — ordering holds by construction, correlations survive, and generation stays fast.

The general principle: a relationship gets tried as a native SDV constraint first, and only stays there if testing shows it doesn't distort anything else. The moment it does, it moves to code that runs after SDV has finished, where it can no longer affect anything else's statistics. That's also the reasoning behind a third, planned-but-not-yet-built rule of the same kind — a "total" column that should equal the product of two others, like quantity × price — see Current limitations.

04 — Services

Service catalog

What each of the nine backend services actually owns, in plain terms.

Gateway
port 3000 · Node / Express
Active

The one door the frontend is allowed to knock on. It checks who you are, then quietly forwards your request to whichever internal service actually does the work — the browser never talks to any other service directly.

Sign-up / login: a user picks a username; behind the scenes that maps to a Supabase-managed email/password account. The two endpoints run different sequences:

  1. POST /auth/signup — validates the username, email, and password (minimum 6 characters, confirmation must match); checks the profiles table for a username or email already in use, rejecting with 409 if either is taken; creates the actual Supabase auth account with email_confirm: true set, so there's no separate email-verification step; inserts the matching profiles row linking that account to the chosen username; and — if that last insert fails for any reason — deletes the auth account it just created, so a failed signup never leaves a half-created account behind.
  2. POST /auth/login — takes a username and password; looks up profiles by username to find the associated email (Supabase's own auth system only knows about emails, never usernames); then hands that email and the password to Supabase's password sign-in, and returns the resulting session token plus the profile row.

Worked example: Priya signs up with username priya_k, email priya@example.com, and a password. The Gateway checks that both are free, asks Supabase to create an auth account for that email/password, then inserts a profiles row — { username: "priya_k", email: "priya@example.com", auth_user_id: "…" } — linking the two. Later, Priya logs in with just priya_k and her password: the Gateway looks up that username, finds priya@example.com behind it, and hands that email/password pair to Supabase — which is the only part of the system that ever actually checks the password.

Everything else requires that session token as a bearer Authorization header. The Gateway verifies it with Supabase, then re-issues the request to the target service with three added headers: x-user-id, x-user-email, and a shared x-internal-service-key that proves the request really came through the Gateway.

Routes it forwards:
/me → project-service /projects → project-service /schema → schema-service /tables → table-service /datagen → datagen-service /reports → report-service /export → export-service

Also rate-limits everything (500 requests / 15 min generally, a stricter 20 / 15 min on /auth to slow down credential-guessing) and answers /health and /ready for uptime monitoring.

Project Service
port 3007 · Node / Express
Active

Owns the two organizing concepts everything else hangs off: a customer (stored as an organisations row — a company or team the data belongs to) and a project (one dataset + dashboard for that customer). Creating a project also provisions a real, isolated Postgres schema (e.g. acme_q1demo — organisation name followed by project name) so that one customer's generated tables can never collide with another's.

A project always has exactly one dashboard record tracking its build status (generating → ready / failed), which is created automatically the moment the project is created.

Deleting a project (DELETE /projects/:id) tears down everything that project owns, in order: every generated table is dropped, the project's physical Postgres schema itself is dropped (DROP SCHEMA … CASCADE), then the dashboards, project_data_models, and schemas rows are removed, followed by each schema's uploaded file and seed-row file in Supabase Storage, and finally the projects row itself. This isn't just implemented — it's been verified end to end against the live database: after deleting two real projects, direct read-only queries confirmed zero orphaned rows in any of those tables, the physical schema was actually gone from pg_namespace, and no storage files were left behind under either project's id.

Key endpoints:
GET /me GET /projects POST /projects GET /projects/:id GET /projects/:id/dashboard DELETE /projects/:id
Schema Service
port 3001 · Node / Express
Active

Where an uploaded file becomes a structured schema. Accepts CSV, JSON, or YAML. For a CSV, it looks at up to the first 25 values in each column and guesses the type (number, date, boolean, email, or text); for JSON/YAML written as an explicit schema, it trusts the types the file declares — including types a CSV can never express, like a fixed set of allowed values (enum).

Every upload answers one question the user is asked directly: "Use my data" (the file's own rows are the real data — no AI or statistics involved) or "Generate mock data" (the file is only a template of columns; the AI/statistics pipeline fills it in). Only the second path triggers a background call to AI Service for example rows — this is a deliberate if check, because spending an AI call on a file that already has real rows would be pure waste.

The upload response returns instantly; example-row generation happens after, tracked as seed_status: pending → generating → ready (or failed, with a one-click retry).

Key endpoints:
POST /schema/upload GET /schema/my GET /schema/seed-status GET /schema/:id POST /schema/:id/seed-rows/retry DELETE /schema/:id
AI Service
port 3005 · Node / Express · internal-only
Active — core

The only service in the whole application allowed to talk to an outside AI provider, and the only one holding those API keys. Every other service that needs a judgment call made — "what do these tables have to do with each other," "what should this KPI's SQL look like," "what does this chart mean" — asks this service, never the AI provider directly.

It supports six interchangeable providers (Groq, OpenAI, Azure OpenAI, Anthropic Claude, Google Gemini, Grok) behind one interface — switching which model powers the whole product is a single environment-variable change, nothing else. See the AI layer deep dive for what each capability actually produces.

Datagen Service + SDV Service
ports 3002 (Node) & 3008 (Python/FastAPI) · both internal-only
Active

Datagen Service is the traffic controller for every column in every table. For each one it decides who is allowed to fill it in: a plain counter or UUID for primary keys; a value picked from a parent table that's already been built, for foreign keys (which is what makes every foreign key valid by construction, not just probably valid); a value sampled straight from the AI's example rows, for free-text columns like names and email addresses that have no learnable statistical pattern; or a call out to SDV, for everything else — quantities, prices, dates, categories.

It also handles a structural rule no statistical model can be trusted with on its own: a "delivery date" is computed as its matching "order date" plus a realistic gap sampled from the real examples, rather than asking SDV to enforce the rule directly — testing showed that distorts every other number in the row (see why example rows matter so much for the measured numbers behind that decision). A second rule of the same shape — a "total" that must equal quantity × price, computed after the fact rather than generated as its own independent number — is designed but not yet built; see Current limitations.

SDV Service is the Python sidecar doing the actual statistics. Given a batch of example rows and an explicit, human-declared type for every column (it is deliberately never allowed to guess a column's meaning from its name — see the callout below), it trains a small generative model and can then produce as many new rows as asked, correlated the same way the examples were. Trained models are cached by a hash of the schema and its examples, so re-generating the same project twice doesn't retrain from scratch.

A real bug this design exists to prevent

Early testing let the statistics library guess what a column meant from its name. A plain column literally named city, holding real city names, was silently reclassified as "personal information" and every value replaced with an invented placeholder name. The data still looked plausible at a glance — that's what made it dangerous. The fix: every column's meaning is now stated explicitly by this application's own code, never inferred.

Datagen endpoints:
POST /datagen/preview POST /datagen/generate POST /datagen/generate-relational GET /datagen/sdv-status
Table Service
port 3003 · Node / Express
Active — core

The factory floor. This is the service the "Generate Tables" button actually calls, and it owns the entire pipeline described in Figure 2 end to end: confirming every schema's example rows are ready, asking AI Service for relationships, working out a safe build order, creating real Postgres tables, asking Datagen Service for rows, inserting them, and building the dashboard.

Row counts per table are not left to the AI's judgment — they're fixed by table role: a fact table (the busy transactional one, like sales) gets 500 rows, a dimension table (like customers or products) gets 50, a small reference table gets 10, and a many-to-many bridge table gets 200. This keeps generated datasets a believable shape without asking the user to think about it.

It also owns the primary path where the AI writes raw SQL directly for a requested KPI instead of filling out a structured plan — see Safety & guardrails for how that SQL is kept from ever doing anything unsafe.

Key endpoints:
POST /tables/projects/:id/generate-tables POST /tables/projects/:id/retry-data-insert GET /tables/projects/:id/data-model GET /tables/generated/:id/rows POST /tables/schemas/:id/build-table
Report Service & Export Service
ports 3004 & 3009 · Node / Express
Not yet implemented

Both exist today only as a health check — a running process with nothing behind it. The Gateway already forwards /reports and /export traffic to them, and their dependency lists (pg, fast-csv, pg-format) show what they're intended to eventually do — generate downloadable exports and standalone reports — but none of that logic has been written yet. Report generation currently happens inline inside Table Service and Project Service instead.

05 — Deep dives

The AI layer, capability by capability

AI Service exposes eight distinct "asks," not one general-purpose chat endpoint. Each one has a narrow, specific job, a prompt tuned for that job, and a hand-written validator that checks the answer before anyone downstream is allowed to trust it.

The repair loop

Every capability below follows the same pattern: build a focused prompt → call the model → strictly parse the response as JSON → run it through a validator written specifically for that shape of answer. If the validator rejects the answer, it doesn't just fail — it sends the rejected answer back to the model along with the specific reason it was wrong, and asks for a fix, up to two or three times, nudging the model's "creativity" setting up slightly each retry so it doesn't just repeat the same mistake. This is what lets the product tolerate an AI model being occasionally wrong without becoming unreliable.

Provider resilience

Every outbound AI call goes through one shared retry policy: up to three attempts on a rate-limit or server error, respecting the provider's own "try again in N seconds" header when it gives one, and failing immediately (no pointless retry) on a genuinely bad request. A shared queue also spaces out every call across the whole service by roughly 1.2 seconds and applies a global cool-down the moment any call hits a rate limit — so ten schemas uploaded at once don't each independently trip the same per-minute limit.

06 — Deep dives

Synthetic data, explained

"Synthetic data" can mean two very different things, and the difference is the whole point of this product.

Faker-style generation (what most tools do, and what this application used to do) fills each column independently — pick a random city, pick a random country, pick a random number — with no column aware of what any other column just picked. It's fast and it's easy, and the result is structurally nonsense: a customer in Tokyo whose country is Brazil, an order total that has nothing to do with its own quantity and price.

This application's approach generates every column of a row together, so the relationships that exist in real data survive into the fake data: a higher-spending customer segment really does show higher order totals; a city really is paired with its real country; a delivery date really does come after its order date. That's the entire reason the pipeline exists in its current, more elaborate two-stage form (AI writes examples, then statistics multiplies them) rather than a single simpler step.

One shortcut worth knowing: if a table only needs 10 rows and there are already 300 good examples sitting around, the pipeline skips training a statistical model entirely and just uses 10 of the examples directly — training a model to produce fewer rows than you already have is both slower and lower quality than the examples themselves.

07 — Deep dives

Safety & guardrails

Nothing an AI model produces is ever executed, stored, or shown to a user just because the model was asked nicely to be careful. Every AI output that matters passes through code written specifically to check it.

The SQL-writing path (LLM-written SQL)

The newest and riskiest capability lets the AI write real SQL directly, rather than filling out a safe structured plan. Table Service treats that SQL as fully untrusted input — parsed into a real syntax tree and walked, checking:

  • Exactly one SELECT statement — no semicolons, no stacked statements, no UNION.
  • Every table referenced must be one this project actually owns; every column must exist in that table's real schema.
  • SELECT * is rejected outright — every column must be named explicitly.
  • Function calls are checked against an allow-list (count, sum, avg, round, ranking functions, and similar) — something like pg_sleep is simply not on the list and is rejected.
  • Anything the checker doesn't specifically recognize is rejected by default, rather than assumed safe.

After a query passes, the service injects its own filter restricting it to the one dataset it's allowed to touch — never something the AI or the user supplies — and forces a row limit and a 5-second query timeout as a last line of defense. A query the validator rejects gets one more chance: it's sent back to the AI with the specific reason, up to twice, before that single KPI is simply dropped from the dashboard rather than failing the whole report.

Failing fast, and failing loudly

Before any physical table is created or any AI call is spent, the pipeline checks two things that used to only surface as a confusing error minutes later: does every schema actually have example rows ready, and is the statistics service (SDV) even reachable. If either check fails, the user gets an actionable message immediately — naming exactly what's missing and how to fix it — instead of a half-built project.

There is deliberately no silent fallback generator. If the statistics engine is unreachable, table generation stops rather than quietly falling back to lower-quality placeholder data that would look fine but mean nothing.

08 — Using the product

The user journey

What actually happens on screen, from an empty account to a finished dashboard.

  1. Sign up and log in.A username, an email, and a password — the app maps that to a managed Supabase account behind the scenes.
  2. Create a project.Name it, attach it to a customer/organization. This provisions a real, private Postgres schema for that project before any data exists.
  3. Upload one or more schema files.CSV, JSON, or YAML. For each file, choose "Use my data" if the file already has real rows, or "Generate mock data" to have the AI + statistics pipeline invent realistic rows from just the column definitions.
  4. Wait for the green light.A status indicator polls in the background; once every uploaded schema shows "seed rows ready," the Generate Tables button unlocks. Uploaded-data schemas skip this step entirely.
  5. Add the KPIs you actually care about, then click "Generate Tables."A progress view walks through relationship inference, table creation, and data generation — the full pipeline from Figure 2 — landing at a finished dataset in well under a minute.
  6. Explore the Schema Playground.A visual, pan-and-zoom diagram of every table and how they relate — drag tables around, hover one to preview its first five rows, click through to see the full table.
  7. Open the Reports page.KPI cards, charts, and a short list of AI-written observations about what the generated data actually shows.
Being upfront about the frontend

A handful of routes from an earlier version of the interface — a standalone schema-upload page, a plain table browser, a storage browser — are still present in the codebase but are no longer linked from the main navigation and, where checked, call a method the current login system doesn't provide. They're safe to ignore; the project-scoped workflow above (Workspace → Playground → Reports) is the one that's actually maintained and current.

09 — Using the product

Use cases & business value

Why this is worth having, stated in business terms rather than engineering ones.

Sales & solution engineering

Demo on a prospect's own data shape, same day

A sales engineer can take a prospect's own column list — with zero real customer data, zero legal review, zero waiting on a data-sharing agreement — and show them a working dashboard built on their actual schema within the same call.

Impact: shortens the gap between "interested" and "convinced" from weeks of procurement to a single meeting.
Product & data teams

Prove out a dashboard before the real pipeline exists

Before committing engineering time to a real ETL pipeline and warehouse, a team can check whether a proposed data model actually supports the KPIs a stakeholder is asking for — because the generated data behaves like the real thing would.

Impact: catches a wrong data model at the design stage, not after a quarter of pipeline work.
Engineering & QA

Realistic test data, with no privacy exposure

Because the "Generate mock data" path never trains on real rows — only on column definitions — there is no real customer information anywhere in the loop. Engineers get data that behaves realistically without a privacy sign-off.

Impact: removes a recurring compliance blocker from everyday development and testing.
Training & onboarding

A disposable, realistic dataset to practice on

New analysts or new hires can build and break dashboards against a dataset that behaves like production, without any risk of touching a real customer's numbers — and it can be regenerated in a minute if something goes wrong.

Impact: shortens ramp-up time without adding any operational risk.

11 — Reference

Glossary

Schema
The structural description of one table — its column names and types — uploaded before any data exists.
Seed rows
A small batch of realistic example rows an AI model writes for a table, used to teach the statistics engine what "realistic" looks like for that data.
SDV (Synthetic Data Vault)
The statistical modeling library that learns how a table's columns relate to each other from seed rows, then generates many more rows following the same patterns.
Blueprint
The AI's structured description of a project's tables, keys, relationships, and dashboard — the shared plan every later pipeline step works from.
Dependency order
The safe sequence to build tables in — lookup ("dimension") tables before the busy transactional ("fact") tables that reference them.
Fact vs. dimension table
A fact table records events (a sale, an order) and changes constantly; a dimension table describes the things involved (a customer, a product) and changes rarely.
Cache key
A fingerprint of a schema's columns and example rows. If it hasn't changed since last time, a previously trained model is reused instead of retrained.
Repair loop
When an AI's answer fails validation, sending it back with the specific error and asking for a fix — instead of failing outright on the first bad answer.
Internal service key
A shared secret every backend service requires on incoming requests, so a service can trust that a request truly came from inside the system.
Physical table
The real table created inside Postgres once a schema's structure is approved — as opposed to the schema definition, which is just a description of what that table should look like.
